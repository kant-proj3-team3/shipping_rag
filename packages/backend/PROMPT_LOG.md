# 프롬프트 개선 기록

프롬프트(`src/backend/prompts.py`)를 바꿀 때마다 가설·변경·측정·채택 판단을 여기에 남긴다. 한 버전에는 가설 하나만 담는다.

## 측정 조건 (모든 버전 공통)

- 문항: development 30 + additional 30 = 60문항. 정답 정보는 서비스에 전달하지 않는다.
- 검색: hybrid_rerank, k=10(팀 결정). 색인 `rag-dev-e2e`(fingerprint `e0e58b07…607224`), 골든 fingerprint `6fb91800…1bef`.
- 모델 `gpt-6-luna`, 생성 온도 0·`reasoning none`(재현성을 위해 측정 때만 `-e`로 덮어씀), 캐시 끔, 같은 버전을 2회 측정.
- 명령: `docker compose … --profile tools run --rm -e LLM_TEMPERATURE=0 -e LLM_REASONING_EFFORT=none cli eval-answer --split development --split additional --mode hybrid_rerank --concurrency 2 --out eval_reports/<이름>.json`
- 보고서 원본은 `eval_reports/`(git 제외)에 있다: `baseline_v2_k10_run{1,2}`, `v3_k10_run{1,2}`, `v4_k10_run{1,2}`.
- 채택 규칙: 2회 평균이 베이스라인 노이즈(회차 간 차이: facts 약 0.03, decision 약 0.02, faithfulness 약 0.03)를 넘어 오르고, 기대 동작(답변/되묻기/보류)이 어긋나는 문항이 늘지 않아야 채택한다.

## 근본 원인 메모 (v2 베이스라인 분석)

- 실패의 대부분은 검색이 근거를 가져오지 못한 문항이다. 근거가 모두 검색된 문항은 decision .96·facts .98, 일부만 검색된 문항은 .446·.411이었다. 프롬프트로 개선할 수 있는 여지는 되묻기 판단과 되묻기 내용에 한정된다.
- 측정 노이즈가 크다: 같은 조건 2회에서 문항 3건 안팎의 결과가 뒤집힌다.

## v2 → v3: 자료에 없다는 이유의 되묻기를 줄인다

- **가설**: 모델이 "자료에 없다"를 이유로 사용자에게 자료를 보내 달라고 되묻는다(과한 되묻기). 되묻기를 사용자만 아는 조건으로 한정하고, 일부만 확인되면 답변하며 확인 안 되는 부분을 짚게 하면 줄어든다.
- **변경**(`_JUDGMENT_STEPS` 4번): answered에 "질문의 일부만 확인되면 이 상태로 두고 확인되지 않는 부분만 짚는다", needs_clarification에 "사용자만 알 수 있는 조건일 때만, 자료에 없다는 이유로 되묻거나 자료 전달을 요청하지 않는다"를 추가.
- **결과**: 답해야 하는데 되묻는 경우가 5~7건 → 1건으로 줄었다. 그러나 decision·facts는 노이즈 범위 안이다(상승 약 +0.02~0.03). 과한 되묻기는 답변이 아니라 보류로 옮겨갔다(IS-DEV-02, DEV-27, ADD-06, ADD-09: 점수 변화 없음, 검색 한계). 되묻기 내용이 좋아진 문항: IS-DEV-30, DEV-12. 
- **부작용**: 보류가 정답인 3문항(IS-DEV-26, ADD-14, ADD-30)이 두 회 모두 "answered"로 바뀌었다. 답 내용은 "확정할 수 없다"로 같고 judge 점수는 유지되지만 상태가 어긋난다. IS-ADD-23은 1회차에서 정답 → 보류.

## v3 → v4: 핵심 결론을 낼 수 없으면 abstained

- **가설**: v3의 "일부 확인되면 answered"가 보류 문항의 상태를 흐린다. 핵심 결론(확정·계산·승인)을 낼 수 없으면 일부 사실을 확인했어도 abstained로 하라고 하면 3문항이 복구된다.
- **변경**: answered를 "자료만으로 질문의 핵심 요청에 답할 수 있다…"로 좁히고, abstained에 "핵심 결론을 자료가 보류하거나 필요한 값이 없어 내릴 수 없으면 일부 사실을 확인했어도 abstained"를 추가.
- **결과**: 기대 보류 문항은 복구됐다(DEV-26, ADD-30, 1회 ADD-14). 그러나 답해야 하는 문항의 보류가 9건으로 늘었다(v3 6~8, v2 2~4). decision은 v3와 같고(.733/.750), faithfulness는 .862/.851로 낮아졌다.
- **판단: 채택하지 않는다.** 점수가 v3보다 오르지 않았고, 상태 어긋남 3건을 고친 대가로 불필요한 보류가 늘었다.

## 현재 결정: v3 유지

- 사전에 정한 규칙(v4가 유의미하게 낫지 않으면 v3로 복귀)에 따라 `PROMPT_VERSION = "v3"`로 되돌렸다.
- 주의: v3, v4 모두 v2 베이스라인 대비 점수 개선은 노이즈 범위 안이다. v3가 확실히 주는 것은 "자료 없음을 이유로 한 되묻기"의 감소뿐이고, 대가로 보류가 정답인 3문항의 상태가 "답변"으로 바뀐다(내용은 보류와 같음).
- 다음 후보(검색 쪽 과제, 팀 합의 필요): 질문을 하위 질문으로 나눠 검색, 예약·창구 같은 문서 유형 문항의 근거 누락. 프롬프트만으로는 한계가 확인됐다.

## 운영 메모

- 측정이 느린 이유: 답변 생성은 3분 안팎이고, 나머지는 채점 호출(RAGAS·Judge)의 모델 API 대기다(GPU·CPU는 유휴). v3 2회차 24분, v4는 병렬 2회 실행 중 1회가 약 65분 멈췄고 다른 1회는 오류 1건(`model_failed`)이 났다. 병렬 실행은 하지 않는다.
- 이미지 재빌드는 약 8분 걸린다.
