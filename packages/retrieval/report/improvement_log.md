## 2. 비교 기반 만들기

### 왜

토큰화나 설정을 바꾼 뒤 점수가 달라졌을 때, 그 차이가 **바꾼 것 때문인지** 아니면 코드 버전·환경·인덱스 차이 때문인지 구별할 수 있어야 한다. 평균만 보면 좋아진 문항과 나빠진 문항이 서로 상쇄되어 안 보이므로 **문항별 비교**도 필요했다.

### 어떻게

| 장치 | 내용 | 이유 |
|---|---|---|
| 기준선 고정 | `baseline/`에 k=5·10·20 결과와 BM25 순위 저장. 코드 상태(커밋과 diff 해시)를 README에 기록 | 나중에 같은 기준과 비교하려고 |
| 같은 조건 | 같은 인덱스(`index_fingerprint`), 같은 골든(`golden_fingerprint`), 같은 k·unit, 같은 GPU 환경 | CLAUDE.md "세 방식은 같은 임베딩·저장소·k·질문으로 비교" |
| 대조군 | 실험용 worktree에서 **바꾸지 않은 설정(regex)**으로 한 번 더 실행 | worktree 환경이 기준선과 같은지 먼저 증명하려고. 결과: 문항별 차이 0 |
| naive 무변화 검사 | BM25를 쓰지 않는 naive는 토큰화를 바꿔도 같아야 한다 | naive가 바뀌면 토큰화 외의 차이가 섞인 것이라 바로 알 수 있음 |
| 문항별 비교표 | 좋아진 문항·나빠진 문항 수, 바뀐 문항 목록, BM25 순위 변화 | 평균에 가려지는 변화를 보려고 |
| DEV / ADD 분리 | 평균을 development·additional로 나눠 봄 | 평가 문항에 맞춰 고치는 것(과적합)을 경계하려고. DEV를 보며 조정하면 ADD로 확인 |
| fingerprint 기록 | 모든 결과 JSON에 두 fingerprint, torch 버전, 장치, 토큰화 방식 기록 | 다른 인덱스끼리 비교하지 않으려고 |

실행 스크립트(평가 러너, BM25 순위 계산, 비교표 생성)는 `app`을 import하므로 모듈 경계 규칙상 `packages/retrieval/` 안에 둘 수 없다. 그래서 저장소 밖 임시 폴더에서 실행하고, 결과물(JSON·md)만 이 폴더에 남겼다.

## 3. 리랭커 입력 한도 (512 / 1024 / 2048)

### 왜

리랭커는 `[CLS] 질문 [SEP] 청크 [SEP]`를 한 입력으로 읽는다. 청크 한도(`max_chunk_tokens`)와 리랭커 한도가 모두 512라서, 설계상으로는 질문이 들어갈 자리가 없다. 넘치면 **오류 없이 청크 뒤쪽이 잘리므로**, 한도를 올려야 하는지 확인했다.

### 어떻게

- 코드를 고치지 않고 `CrossEncoderReranker(max_tokens=n)`으로 값만 바꿔 끼웠다. 상수를 고치는 것과 결과가 같고, 실험이 끝난 뒤 되돌릴 것이 없다.
- 청크 로딩과 BM25는 한 번만 만들고 리랭커만 바꿨다. 그래야 리랭커에 들어가는 후보 50개가 세 설정에서 똑같다.
- 실제로 리랭커에 들어간 질문+청크 쌍 2,800개(56문항 × 50개)의 길이를 잘라내지 않고 다시 셌다.

### 결과와 결정

- 세 값에서 Hit·Recall·문항별 점수·상위 5개 순위·시간이 모두 같았다. 가장 긴 쌍이 504토큰이라 512에서도 잘린 쌍이 없었다.
- **512 유지.** 청킹·임베더 한도와도 맞다.
- 다만 여유가 8토큰뿐이다. `check_chunk_limit`는 질문 길이를 세지 않으므로 "잘리지 않는다"는 코드가 보장하는 성질이 아니라 이번 질문에서 잰 결과다. 청크나 질문이 길어지면 다시 잰다. 그때는 `RERANKER_MAX_TOKENS=1024`로 환경변수만 바꾸면 된다(속도 차이 없음).

## 4. BM25 한국어 토큰화

### 4.1 문제 발견

`IS-ADD-10`이 k=20에서도 세 방식 모두 Hit=0이라 원인을 추적했다.

| 확인한 것 | 결과 |
|---|---|
| 근거 청크가 색인에 있나 | 있다. `IS04-p1-c1`에 규칙 문장이 온전히 들어 있다 → 청킹 문제 아님 |
| Dense 순위 | 31위 |
| BM25 순위 | 480위 → RRF로 합칠 때 50위 밖으로 밀려 리랭커가 보지 못함 |
| BM25가 낮은 이유 | 질문의 `정정합니다`, `vgm을`과 근거의 `정정은`, `vgm의`가 **다른 단어**로 취급됨. 겹치는 단어는 `접수`, `신규`처럼 흔한 단어뿐 |

기존 토큰화는 `re.findall(r"\w+(?:-\w+)*", text.lower())`다. 띄어쓰기 단위로 자르기 때문에 한국어 조사가 단어에 붙은 채로 남는다.

### 4.2 영향 범위 먼저 파악

토큰화는 hybrid·hybrid_rerank의 **모든 질문**에 영향을 준다. 바꾸기 전에 어떤 문항이 움직일지 미리 분류했다.

| 분류 | 문항 | 의미 |
|---|---|---|
| BM25가 점수를 깎은 문항 | 15개 | 토큰화 개선으로 회복을 기대 |
| Dense·BM25 둘 다 50위 밖인 근거 그룹 | 20문항, 29그룹 | BM25가 좋아져야만 구제 가능 |
| 지금 BM25 덕을 보는 문항 | 23개 | **회귀 위험.** 특히 `GR26-P0670` 같은 식별자 정확 일치에 기대는 문항 |

세 번째 분류 때문에 "식별자를 쪼개지 않는다"를 처음부터 조건으로 잡았다.

### 4.3 설계: 환경변수로 방식 선택

```python
BM25_TOKENIZER = regex(기본) | josa | kiwi
```

| 결정 | 이유 |
|---|---|
| 기본값은 기존 `regex` | 설정하지 않으면 지금과 똑같이 동작해야 함 |
| 환경변수로 선택 | 같은 코드로 세 방식을 같은 조건에서 비교할 수 있음. 설정은 환경변수로 읽는다는 팀 규칙과도 맞음 |
| `Bm25Index`가 토큰화 함수를 한 번 정해서 보관 | **색인과 질의가 반드시 같은 토큰화를 쓰도록.** 둘이 다르면 BM25가 의미 없어짐 |
| `kiwipiepy`는 kiwi를 고를 때만 import | 선택 의존성이라 다른 방식이나 테스트에는 영향이 없게 |
| 재색인 불필요 | BM25는 시작할 때 Qdrant의 청크로 메모리에서 만들므로 `index_fingerprint`가 그대로 → 기준선과 바로 비교 가능 |

### 4.4 1차 구현과 발견한 문제

1차 구현은 이랬다.
- **josa**: 단어 끝의 흔한 조사(`은 는 이 가 을 를 의 에 로 도 만 과 와 …`)를 긴 것부터 뗀다
- **kiwi**: Kiwi 형태소 분석 결과에서 명사·동사 어간·외국어·숫자만 남긴다

실제 문장과 청크에 돌려 보니 **전문용어·복합명사를 잘못 나누는** 문제가 있었다.

| 방식 | 원문 | 1차 결과 | 문제 |
|---|---|---|---|
| josa | `정확도` | `정확` | 명사의 끝 글자 `도`를 조사로 착각 |
| josa / regex | `B/L` | `b`, `l` | `/`에서 잘림 |
| kiwi | `선적서류` | `선적`, `서류` | 복합명사 분해 |
| kiwi | `컨테이너터미널` | `컨테이너`, `터미널` | 복합명사 분해 |
| kiwi | `GR26-P0670` | `gr`, `26`, `p`, `0670` | 식별자 분해 |
| kiwi | `P26-20-0670` | `p` | 일련번호(`W_SERIAL`) 품사를 버림 |
| kiwi | 이메일 주소 | (사라짐) | `W_EMAIL` 품사를 버림 |

### 4.5 2차 수정: 원칙 "전문용어·복합명사를 나누지 않는다"

검색 대상이 해운 업무 문서라 `선적서류`, `화물총중량`, `B/L`, 예약·장비 번호처럼 **붙여 쓴 전문용어와 식별자가 검색의 핵심 단서**다. 이걸 쪼개면 흔한 단어(`서류`, `중량`)와 일치하는 청크가 늘어 변별력이 떨어진다. 그래서 "조사는 떼되 단어 안쪽은 건드리지 않는다"를 원칙으로 다시 고쳤다.

**josa 수정**

| 수정 | 이유 |
|---|---|
| 한 글자 조사 `이 가 도 과 와 의 로 만`은 떼지 않는다 | 명사의 끝 글자와 겹친다: `결과`, `효과`, `경로`, `항로`, `회의`, `합의`, `정확도`, `한도`, `평가`, `원가`, `차이`, `미만` |
| `은 는 을 를 에`와 두 글자 이상 조사만 뗀다 | 명사 끝에 거의 오지 않아 잘못 뗄 위험이 낮다 |
| 남는 부분이 두 글자 미만이면 떼지 않는다 | `건은`→`건`처럼 너무 짧아지면 다른 단어와 구별이 안 된다 |
| 영문·숫자를 `/`로 이은 약어(`B/L`, `D/O`)를 한 단어로 | 해운 약어가 `/`로 쓰인다 |

대가: `이메일로`처럼 `로`가 진짜 조사인 경우도 떼지 못한다. 잘못 자르는 것보다 덜 자르는 쪽을 택했다.

**kiwi 수정: 형태소를 다시 조립하지 않고, 자를 위치만 Kiwi에 맡긴다**

처음에는 Kiwi가 나눈 명사 형태소를 다시 붙이는 방식(`선적`+`서류`→`선적서류`)으로 고쳤다. 그런데 실제 청크(표 형식)에서 Kiwi의 품사 판단이 자주 틀렸다.

| 원문 | Kiwi 분석 | 재조립 결과 |
|---|---|---|
| `화물총중량` | 화물/NNG + 총/**MM**(관형사) + 중량/NNG | `화물`, `중량` |
| `1대` | 1/SN + 대/**XPN**(접두사) | `1` |
| `기록일` | 기록/NNG + 이/**VCP**(이다) + ㄹ/ETM | `기록` |

형태소 단위로 다시 조립하는 방식으로는 이런 오분석을 끝없이 예외 처리해야 한다. 그래서 방식을 바꿨다.

> **띄어쓰기 단어를 기준으로 하고, Kiwi는 그 단어 끝의 조사·어미가 어디서 시작하는지만 판단한다.**

단어 안쪽은 절대 나누지 않으므로 복합명사·단위·식별자가 원문 그대로 남는다. josa와의 차이는 "어디서 자를지"를 규칙 목록으로 정하느냐(josa), 형태소 분석으로 정하느냐(kiwi)뿐이라 비교하기에도 깔끔하다.

이후 세부 수정:

| 문제 | 수정 | 이유 |
|---|---|---|
| `기록일` → `기록` (이다로 오분석) | 지정사(VCP)는 표기가 `이·입·인·임·였`으로 시작할 때만 뗀다 | `예정입니다`, `대상이며`는 떼고, 표 머리글 `기록일`은 지킨다 |
| 위 수정 뒤에도 `기록` | 멈춘 형태소가 끝나는 위치보다 앞에서는 자르지 않는다 | `일` 한 글자에 `이`와 `ㄹ` 두 형태소가 같은 위치로 겹쳐서, `ㄹ` 위치에서 이미 잘렸다 |
| `별도`→`별`, `문의`→`문`, `이의`→`이` | 남는 부분이 두 글자 미만이면 자르지 않는다(josa와 같은 규칙) | Kiwi가 두 글자 명사의 끝을 조사로 읽는 경우 |
| 일련번호·이메일이 사라짐 | (재조립 방식을 버리면서 자연히 해결) | 단어를 원문 그대로 두므로 품사와 무관 |

대가: `건도`→`건`처럼 맞게 자를 수 있던 짧은 단어도 원형으로 남는다. PDF 원문에서 띄어쓰기가 빠진 `대상을묶지` 같은 곳은 한 단어로 처리된다.

### 4.6 검증

| 검증 | 방법 | 결과 |
|---|---|---|
| 실제 청크 무작위 표본 | 청크 4개에 두 방식을 적용해 눈으로 확인 | 1차에서 `화물총중량`·`기록일`·`1대` 문제 발견 → 4.5에서 수정 |
| 전체 청크 감사 | 청크 15,053개에서 kiwi가 떼어 낸 한 글자 끝을 모두 모아 단어별로 확인 | 수정 후에는 `대상과`→`대상`, `별도로`→`별도`, `처리결과도`→`처리결과`처럼 실제 조사만 뗌 |
| 단위 테스트 | 용어를 나누지 않는 규칙을 테스트로 고정 | `선적서류`, `컨테이너터미널`, `화물총중량`, `1대`, `기록일`, `별도`, `문의`, `B/L`, `P26-20-0670` 포함. retrieval 테스트 65개, import_lint 통과 |
| 처리 시간 | kiwi로 청크 15,053개 토큰화 | 15.0초 (api 시작 시 한 번) |

테스트를 만들다 생긴 실수도 기록한다. 문서가 하나뿐인 BM25 테스트는 IDF가 음수가 되어 점수가 0 이하로 나온다. 코드가 아니라 테스트를 고쳤다(관계없는 문서를 함께 둠). `로써`는 조사 목록에 없는데 테스트에 썼다가 실패했다. 목록을 테스트에 맞추지 않고 테스트 예시를 바꿨다.

| BM25 50위 안 근거 그룹 (178개 중) | 133 | 136 | **144** |
| BM25 최고 순위 중앙값 | 7 | 8 | **5** |
| Hybrid Recall@20 | 0.794 | 0.779 | 0.770 |
| Hybrid + Rerank Recall@20 | 0.808 | 0.817 | 0.820 |

**결정: regex 유지.** 이유:
1. **최종 지표 변화가 작고 방향이 엇갈린다.** 대부분 ±0.02 안이고 DEV는 떨어지고 ADD는 오른다. 56문항에서는 우연과 구별하기 어렵다.
2. **문항별로는 많이 바뀐다.** Hybrid k=20, kiwi: 7문항 개선, 11문항 하락. 평균이 비슷한 건 상쇄 효과다.
3. **크게 나빠진 문항이 있다.** `IS-DEV-28`은 근거 그룹 BM25 순위가 10→56위, 3→159위로 떨어졌다. 조사를 떼면서 `청구`·`대상`·`필요` 같은 흔한 단어가 더 많은 청크와 일치하게 된 것으로 보인다(검증하지 않은 가설).
4. **비용이 있다.** `kiwipiepy` 의존성과 팀 공용 `uv.lock` 변경, 유지할 규칙이 늘어난다.
5. **목표 문항도 못 살렸다.** `IS-ADD-10`의 BM25 순위는 205→113(josa)·140(kiwi)위로 올랐지만 50위 안에는 못 들었다.

**남긴 단서**: kiwi는 BM25 단독 순위를 분명히 개선했다. 그런데도 최종 결과가 그대로라는 건 개선이 **RRF 결합 단계에서 묻힌다**는 신호일 수 있다. 결합 방식(가중치, `RRF_CONSTANT`)을 바꾸게 되면 kiwi를 다시 비교할 가치가 있다.

### 4.8 코드 보존

실험 코드는 커밋하지 않고 worktree와 함께 지웠다. 다시 시험할 수 있도록 최종 버전의 핵심을 남긴다(`hybrid.py`에 추가했던 부분).

```python
BM25_TOKENIZER_ENV = "BM25_TOKENIZER"
DEFAULT_BM25_TOKENIZER = "regex"

_JOSA = sorted(
    {
        "으로부터", "에서부터", "으로써", "으로서", "에게서", "이라도", "이라는", "이라고",
        "에서는", "에서도", "으로는", "으로도", "까지는", "까지도", "부터는", "에게는", "에는", "에도",
        "에서", "에게", "한테", "으로", "부터", "까지", "마다", "처럼", "라도", "이며", "이고", "이다",
        "은", "는", "을", "를", "에",
    },
    key=len,
    reverse=True,
)
_HANGUL_END = re.compile(r"[가-힣]$")
# 하이픈 식별자(R-0021)와 영문·숫자를 '/'로 이은 약어(B/L)는 한 단어
_WORD = re.compile(r"[a-z0-9]+(?:/[a-z0-9]+)+|\w+(?:-\w+)*")


def _strip_josa(token: str) -> str:
    if not _HANGUL_END.search(token):
        return token
    for josa in _JOSA:
        if token.endswith(josa) and len(token) - len(josa) >= 2:
            return token[: -len(josa)]
    return token


def tokenize_josa(text: str) -> list[str]:
    return [_strip_josa(t) for t in _WORD.findall(text.lower())]


_VCP_SURFACES = ("이", "입", "인", "임", "였")


def _is_suffix_tag(tag: str) -> bool:
    return tag.startswith(("J", "E")) or tag in {"XSV", "XSA", "VCP"}


class KiwiTokenizer:
    def __init__(self) -> None:
        from kiwipiepy import Kiwi
        self._kiwi = Kiwi()

    def __call__(self, text: str) -> list[str]:
        lowered = text.lower()
        morphs = self._kiwi.tokenize(lowered)  # 문장 전체를 한 번에 분석해 문맥을 살린다
        tokens, mi = [], 0
        for word in _WORD.finditer(lowered):
            start, end = word.span()
            while mi < len(morphs) and morphs[mi].start < start:
                mi += 1
            inside, j = [], mi
            while j < len(morphs) and morphs[j].start + morphs[j].len <= end:
                inside.append(morphs[j])
                j += 1
            tokens.append(word.group()[: self._cut(inside, lowered, start, end) - start])
        return tokens

    @staticmethod
    def _cut(inside, text: str, start: int, end: int) -> int:
        cut, keep_until = end, start
        for m in reversed(inside):
            guarded_vcp = m.tag == "VCP" and not text.startswith(_VCP_SURFACES, m.start)
            if not _is_suffix_tag(m.tag) or guarded_vcp:
                keep_until = m.start + m.len
                break
            cut = m.start
        cut = max(cut, keep_until)
        return end if cut - start < 2 else cut


def select_tokenizer(name: str | None = None):
    chosen = (name or os.environ.get(BM25_TOKENIZER_ENV) or DEFAULT_BM25_TOKENIZER).strip().lower()
    if chosen == "regex":
        return tokenize
    if chosen == "josa":
        return tokenize_josa
    if chosen == "kiwi":
        return KiwiTokenizer()
    raise ValueError(f"{BM25_TOKENIZER_ENV}는 regex, josa, kiwi 중 하나여야 한다: {chosen}")

# Bm25Index.__init__(self, chunks, tokenizer=None):
#     self._tokenize = tokenizer or select_tokenizer()   # 색인·질의에 같은 함수를 쓴다
```

## 5. 응답 지연 분석 (개선안만 정리, 미적용)

### 왜

UI에서 질문할 때 `latency_ms`가 가끔 매우 길게 나왔다.

### 어떻게 찾았나

- `latency_ms`가 무엇을 재는지부터 확인했다. 서버가 요청을 받아 응답할 때까지의 시간이다. 당시 백엔드는 목업이라 LLM 시간이 없었으므로 사실상 검색 시간이다.
- 프론트 기본 방식(`hybrid_rerank`)과 api 실행 환경(CPU torch)을 확인한 뒤, api와 같은 환경에서 방식별로 측정했다.

| 방식 | 질문당 시간 (CPU, 순서대로) |
|---|---|
| naive | 0.03 ~ 0.09초 |
| hybrid | 0.08 ~ 0.18초 |
| hybrid_rerank | **8.4 ~ 17.4초** |
| hybrid_rerank 3개 동시 | 15.3 / **36.3** / 22.8초 |

### 원인

| 원인 | 근거 |
|---|---|
| CPU에서 리랭킹 | 시간의 99% 이상이 리랭커. GPU에서는 질문당 약 1.3초 |
| 리랭커 잠금 대기 | 한 번에 하나만 계산. 동시 요청이나 중지 뒤 재질문은 앞 계산이 끝날 때까지 기다림. 프론트에서 중지해도 서버의 계산은 계속됨 |
| 첫 요청의 모델 로딩 | 리랭커를 처음 쓸 때 불러옴(GPU에서 로딩과 첫 호출 4.6초) |
| 질문마다 다른 입력 길이 | 배치는 가장 긴 입력에 맞춰 계산됨. 후보 최장 길이가 질문마다 215~487토큰 |
| Docker에서 모델 재다운로드 | 리랭커가 `RAG_MODEL_CACHE`를 쓰지 않아, 컨테이너를 새로 만들면 첫 리랭킹에서 약 2.2GB를 다시 받음 |

### 개선안 (아직 적용하지 않음)

| 개선안 | 이유 | 상태 |
|---|---|---|
| 리랭커 `CrossEncoder`에 `cache_folder=RAG_MODEL_CACHE` 전달 | Docker에서 모델 재다운로드 방지. 임베더는 이미 이렇게 한다 | 다음 PR 후보 |
| 시작 시 리랭커 미리 불러오기 | 첫 요청의 로딩 시간 제거 | 검토 |
| latency 측정을 잠금 대기와 분리 | 질문 자체의 비용과 대기 시간을 구별해 보려고 | 검토 |
| 리랭킹 후보 수 조정 (50 → 더 적게) | 계산량에 비례해 빨라짐 | Recall 영향을 평가로 확인한 뒤 결정 |
| GPU에서 fp16 | 더 빨라질 수 있음 | 점수 변화 검증 필요 |
| 요청마다 하는 청크 사전 복사 제거 | `by_id`가 이미 모든 청크를 가지고 있어 불필요 | 작은 비용, 검토 |

dev 반영 후 저장소 기본 환경이 CUDA torch(2.11.0+cu128)로 바뀌었으므로, CPU 기준 지연은 GPU 환경에서 다시 재야 한다.

## 6. 평가 환경을 정비하며 고친 것

품질 개선은 아니지만, 평가가 **목업이 아니라 실제 구현으로** 돌아가게 하려고 고친 것들이다.

| 문제 | 수정 | 이유 |
|---|---|---|
| `.env`에 `CHUNKING_IMPL`·`RETRIEVAL_IMPL`이 없음 | `real`로 설정 | 기본값이 `mock`이라 실제 인덱스가 아니라 목업으로 평가될 뻔함 |
| `RETREIVAL_IMPL` 오타 | `RETRIEVAL_IMPL`로 수정 | 철자가 다르면 설정이 없는 것과 같아 검색이 목업으로 돎 |
| `INDEX_NAME`이 실제 컬렉션과 다름 | `rag-dev-chanyeongg3`로 수정 | 인덱스를 못 찾아 평가가 실행되지 않음 |
| `PYTHONUTF8=1`을 `.env`에 넣음 | 지우고 터미널에서 설정 | UTF-8 모드는 파이썬 시작 시점에 정해져서, 시작 뒤에 읽는 `.env`로는 효과가 없음 |
| `.env.example`에 `real` 기본값 | 빈 값으로 되돌림 | 공용 파일이라 팀원 모두가 실제 모델·색인이 필요한 상태로 시작하게 됨 |
| `CORS_ALLOW_ORIGINS=   # 주석` | 주석을 윗줄로 옮김 | `.env` 로더가 "빈 값 + 같은 줄 주석"의 주석을 값으로 읽음(`app/envfile.py`의 버그, 담당자에게 알릴 것) |

이후 dev의 PR #33이 `APP_IMPL=real`을 기본값으로 바꿔서, 앞의 `*_IMPL` 설정은 지금은 필요 없다.

## 7. 배운 것

- **평균보다 문항별 변화를 본다.** 토큰화 실험에서 평균은 거의 같았지만 문항은 18개가 움직였다.
- **대조군을 먼저 돌린다.** 환경이 기준선과 같다는 걸 증명해야 차이를 해석할 수 있다.
- **바꾸기 전에 영향 범위와 회귀 위험을 분류한다.** "BM25 덕을 보는 문항"을 먼저 찾았기 때문에 식별자 보존을 처음부터 조건으로 넣을 수 있었다.
- **샘플이 아니라 전체 데이터로 감사한다.** 몇 문장 예시로는 `별도`→`별` 같은 오류가 보이지 않았다. 전체 청크에서 떼어 낸 끝을 모아 보고서야 드러났다.
- **형태소 분석기를 믿을 범위를 정한다.** 표 형식 텍스트에서는 품사 판단이 자주 틀렸다. 분석기에는 "어디서 자를지"만 맡기고, 단어 안쪽은 원문을 지키는 방식이 더 안전했다.
- **좋아진 중간 지표가 최종 지표로 이어지지 않을 수 있다.** BM25 순위 개선이 RRF 결합에서 묻혔다. 다음 개선 대상은 결합 단계다.
