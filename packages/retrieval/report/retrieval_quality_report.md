# 검색 품질 평가 보고서

- 작성일: 2026-11-11
- 대상: retrieval 모듈의 세 검색 방식 (Naive / Hybrid / Hybrid + Rerank)
- 평가 단위: **page**(정확한 근거 페이지)와 **document**(근거 문서) 두 가지를 같은 조건으로 평가했다
- 코드: retrieval 구현은 `origin/dev`(`e93cefd`)와 동일 (PR #19 리뷰 반영본 `06f7021`)

## 1. 요약

| 항목 | 결과 |
|---|---|
| 가장 좋은 방식 | **Hybrid + Rerank**. page·document 모두 모든 k에서 Recall이 가장 높다. 다만 document k=20은 Hybrid와 사실상 같다(0.899 vs 0.897) |
| k=5 (Hybrid + Rerank) | page: Hit **0.964**, Recall **0.676** / document: Hit **1.000**, Recall **0.785** |
| k=10 (Hybrid + Rerank) | page: Hit **0.982**, Recall **0.765** / document: Hit **1.000**, Recall **0.863** |
| 문서 단위 Hit | 세 방식 모두 k=10부터 1.000이다(Hybrid k=5만 0.982). 문서 단위에서는 Hit로 방식을 구분할 수 없고 Recall로 구분된다 |
| 놓치는 것은 주로 페이지 | page에서 Hit=0이던 문항은 Hybrid k=5의 `IS-ADD-01`을 빼면 모두 document에서는 찾아진다. 맞는 문서는 가져오는데 정확한 페이지를 놓치는 경우다 |
| Hybrid(BM25 결합) vs Naive | page k=5에서는 Hybrid가 낮다(Recall 0.596 vs 0.619). document에서는 Recall이 모든 k에서 Hybrid가 높다 |
| 끝까지 못 찾는 문항 | page 기준 `IS-ADD-10` 1개(k=20, 세 방식 공통). document 기준으로는 모든 방식이 찾는다 |
| 비용 | 리랭킹이 질문당 약 1.3초(GPU)로 검색 시간 대부분을 차지한다 |

**권고**: 기본 검색 방식은 Hybrid + Rerank, k는 5~10을 쓴다. 답변에 문서명과 페이지를 출처로 붙이는 서비스이므로 page 기준을 주 지표로 보고, document 기준은 "문서를 못 찾는지, 페이지를 못 찾는지"를 구분하는 데 쓴다. BM25 토큰화와 리랭커 입력 한도는 현재 설정(정규식 토큰화, 512)을 유지한다. 근거는 5·6장의 추가 실험이다.

### 2.2 검색 방식

| 방식 | 동작 |
|---|---|
| Naive | E5 임베딩 Dense 검색 상위 k개 |
| Hybrid | Dense 상위 50개와 BM25 상위 50개를 RRF(상수 60)로 합친 뒤 상위 k개 |
| Hybrid + Rerank | Hybrid로 합친 순위의 상위 50개를 cross-encoder로 다시 채점한 뒤 상위 k개 |

| 구성 요소 | 값 |
|---|---|
| 임베더 | `intfloat/multilingual-e5-base` (`prefix=e5, norm=l2, max=512, dim=768`) |
| 리랭커 | `BAAI/bge-reranker-v2-m3`, 입력 한도 512 |
| BM25 토큰화 | 소문자 변환 후 `\w+(-\w+)*` (하이픈 식별자는 한 토큰) |
| 후보 수 | Dense·BM25 각 50개, 리랭킹 50개 (`CANDIDATE_POOL`) |

### 2.3 지표

- **근거 그룹 기준 채점.** 그룹끼리는 AND, 그룹 안의 후보는 OR다. 그룹 안의 후보 중 하나라도 검색 결과에 있으면 그 그룹은 충족된다.
- **Hit@k**: 충족한 그룹이 하나라도 있으면 1, 없으면 0
- **Recall@k**: 충족한 그룹 수 / 전체 그룹 수
- **단위(unit)**는 호출자가 명시한다(기본값 없음). 이 보고서는 두 단위를 모두 평가했다.

| 단위 | 일치 조건 | 보는 것 |
|---|---|---|
| `page` | 검색된 청크의 `[page_start, page_end]`가 근거 페이지를 포함 | 정확한 근거 페이지를 찾는가 |
| `document` | 검색된 청크의 `book_id`가 근거 문서와 같음 | 맞는 문서를 찾는가 |

- document 기준은 page 기준보다 조건이 느슨하다. 모든 문항·방식·k에서 document로 충족한 그룹이 page로 충족한 그룹을 포함하는지 확인했고, 위반은 0건이었다.
- 평균은 채점 문항(56개)만으로 계산한다. 근거 없음·검색 실패 문항은 0점으로 넣지 않고 건수만 보고한다.

## 4. 분석

### 4.1 Hybrid + Rerank가 가장 좋다

- page에서는 모든 k에서 Hit·Recall이 가장 높고, Recall 1.0 문항 수도 가장 많다. document에서도 Recall은 모든 k에서 가장 높고 Recall 1.0 문항 수도 가장 많다.
- 리랭킹의 효과는 **작은 k에서 크다.** Recall 차이는 다음과 같다(k=5 / 10 / 20).

| 비교 | page | document |
|---|---|---|
| Rerank − Naive | +0.057 / +0.076 / +0.076 | +0.059 / +0.073 / +0.050 |
| Rerank − Hybrid | +0.080 / +0.065 / +0.015 | +0.049 / +0.040 / +0.002 |

- 리랭커는 후보 50개의 **순서만** 바꾼다. 그래서 k가 50에 가까워지면 Hybrid와 결과 집합이 같아진다. document k=20에서는 Rerank와 Hybrid가 사실상 같다(0.899 vs 0.897). 리랭킹의 가치는 상위 몇 개 안에 좋은 근거를 끌어올리는 데 있다.

### 4.2 Hybrid와 Naive의 우열은 단위에 따라 다르다

| 비교 (Hybrid − Naive) | k=5 | k=10 | k=20 |
|---|---|---|---|
| page Recall | −0.023 | +0.011 | +0.061 |
| document Recall | +0.010 | +0.034 | +0.048 |
| page Hit | −0.036 | −0.036 | 0 |
| document Hit | −0.018 | 0 | 0 |

- page k=5에서 Hybrid는 Naive보다 낮다(Recall 0.596 < 0.619). 그런데 document에서는 모든 k에서 Hybrid의 Recall이 높다.
- Hybrid가 page k=5에서 근거를 하나도 못 찾은 문항은 7개인데, 그중 6개는 document 기준으로는 찾았다. BM25 결합이 맞는 문서는 가져오지만 상위 5개 안에 정확한 페이지를 넣지는 못하는 경우가 Naive보다 많다는 뜻이다.
- BM25 토큰화가 띄어쓰기 단위라 한국어 조사가 붙은 채로 비교된다(`정정합니다` ↔ `정정은`). 이 영향을 5.3절에서 실험했다.

### 4.3 맞는 문서를 찾고도 페이지를 놓친다

- 세 방식 모두 page Recall이 document Recall보다 0.09~0.14 낮다(3.6절). 근거 그룹으로 세면 page에서 document로 바꿀 때 충족 그룹이 16~21개(178개의 9~12%) 늘어난다. 이만큼의 근거 그룹은 "맞는 문서는 가져왔지만 정확한 페이지는 못 가져온" 경우다.
- 반대로 document에서도 Recall은 0.9 안팎에 머문다. k=20에서도 Hybrid와 Hybrid + Rerank 모두 154/178개만 충족한다. 나머지 24개 그룹은 문서 자체를 가져오지 못했다. 근거 그룹이 서로 다른 문서에 걸친 문항이 있다(예: `IS-DEV-28`은 `IS42`·`IS20`·`IS13`).
- 그래서 두 지표를 같이 봐야 어느 단계(문서 선정 / 페이지 선정)에서 놓치는지 구분된다.

### 4.4 실패 사례: `IS-ADD-10`

| 항목 | 내용 |
|---|---|
| 질문 | 11월 2일 이메일로 접수 완료된 40GP VGM을 11월 5일 정정합니다. 정정일이 포털 전환 뒤니까 포털에 신규 등록해야 하나요? |
| 정답 근거 | `IS04` 1페이지, 근거 그룹 1개, 후보 1개 |
| document 결과 | **모든 방식·모든 k에서 Hit 1.** `IS04` 문서는 상위에 있다(예: Naive 3위 `IS04` p56, Hybrid + Rerank 1위 `IS04` p53) |
| page 결과 | 모든 방식·모든 k에서 Hit 0. 정확한 페이지(p1)를 가져오지 못한다 |
| 근거 청크 | `IS04-p1-c1`. 규칙 문장 4개가 한 청크에 온전히 들어 있다(청킹 문제 아님) |
| Naive 순위 | 31위 |
| BM25 순위 | 480위 (그룹 기준 최고 205위) |
| Hybrid·Rerank | 합친 순위 50위 밖이라 리랭커가 보지 못함 |
| 리랭커 점수 | 근거 청크를 직접 넣으면 0.49. 상위 청크는 0.96~0.99 |

이 문항은 문서를 못 찾는 것이 아니라 **같은 문서의 다른 페이지를 먼저 가져와서** 정확한 페이지를 놓친다.

**원인**
1. **질문과 근거의 표현 차이.** 질문은 날짜·장비가 있는 구체적 사례이고, 근거는 일반 규칙이다. 날짜·장비가 비슷한 사례 청크가 더 높게 평가된다.
2. **BM25의 조사 문제.** 질문의 `정정합니다`, `vgm을`과 근거의 `정정은`, `vgm의`가 다른 단어로 취급된다.
3. **정답 근거가 하나뿐이다.** 상위에 오른 `IS04` p53(“전환 이후 요청이지만 신규 등록이 아니라 기존 … 경로를 따른 정정으로 관리한다”)과 `IS08` p19(“이미 접수된 자료는 새 포털에 중복 제출하지 않는다”)도 같은 답을 뒷받침하지만, 근거 후보로 등록되어 있지 않아 page 기준으로는 0점이다. 평가 파일의 `grading_notes`도 “다른 충분한 원문도 인정”한다고 적고 있으므로, **답변 평가에서는 맞을 가능성이 있다**(확인하지 않음).

## 5. 추가 실험

5.1~5.3의 실험은 **unit=page** 기준이다.

### 5.1 CPU와 GPU의 결과 차이

같은 조건(k=5, page)으로 CPU(torch 2.15.0+cpu)와 GPU(torch 2.14.1+cu130)에서 돌렸다.

| 방식 | 문항별 결과가 다른 문항 | CPU 시간 | GPU 시간 |
|---|---|---|---|
| Naive | 0 / 60 | 1.6초 | 1.6초 |
| Hybrid | 0 / 60 | 8.4초 | 10.4초 |
| Hybrid + Rerank | 0 / 60 | 798.5초 | 118.6초 |

→ **실행 기기는 점수에 영향을 주지 않았다.** 두 실행을 동시에 돌렸으므로 시간은 참고용이다.

### 5.2 리랭커 입력 한도 (512 / 1024 / 2048)

| max_tokens | Hit@5 | Recall@5 | 점수가 바뀐 문항 |
|---|---|---|---|
| **512** | 0.964 | 0.676 | 기준 |
| 1024 | 0.964 | 0.676 | 0 / 56 |
| 2048 | 0.964 | 0.676 | 0 / 56 |

- 리랭커에 실제로 들어간 질문+청크 쌍 2,800개 중 가장 긴 것이 504토큰이라 512에서도 잘린 쌍이 없었다.
- 세 설정에서 상위 5개 목록이 바뀐 질문이 없으므로, document 기준 결과도 같다.
- → **512를 유지한다.** 여유가 8토큰뿐이라 청크 길이나 질문이 길어지면 다시 잰다. 자세한 내용은 `reranker_max_tokens.md`.

### 5.3 BM25 토큰화 (regex / josa / kiwi)

k=5·10·20, unit=page로 비교했다.

| 방식 | 토큰화 |
|---|---|
| regex (현재) | 띄어쓰기 단위 |
| josa | 단어 끝의 조사를 규칙으로 뗌. 명사 끝 글자와 겹치는 한 글자 조사는 떼지 않음 |
| kiwi | Kiwi 형태소 분석으로 단어 끝 조사·어미 위치만 판단해 뗌. 복합명사·식별자는 나누지 않음 |

| 지표 | regex | josa | kiwi |
|---|---|---|---|
| BM25 50위 안 근거 그룹 (178개 중) | 133 | 136 | **144** |
| BM25 최고 순위 중앙값 | 7 | 8 | **5** |
| Hybrid Recall@20 | 0.794 | 0.779 | 0.770 |
| Hybrid + Rerank Recall@5 | 0.676 | 0.685 | 0.681 |
| Hybrid + Rerank Recall@20 | 0.808 | 0.817 | 0.820 |

- kiwi는 BM25 단독 순위를 뚜렷하게 개선했다(근거 그룹 101개 순위 상승, 47개 하락).
- 하지만 **최종 Hit·Recall 변화는 대부분 ±0.02 안**이고, DEV는 떨어지고 ADD는 오르는 등 방향이 엇갈린다. 문항별로는 좋아진 것과 나빠진 것이 서로 상쇄된다(Hybrid k=20, kiwi: 7문항 개선, 11문항 하락).
- → **regex를 유지한다.** 의존성 추가(`kiwipiepy`)를 감수할 만큼 개선이 분명하지 않다. 자세한 내용은 `variants/summary.md`.
- 이 비교는 page 기준이다. document 기준으로도 같은 결론인지는 확인하지 않았다.

## 6. 처리 시간

GPU, 60문항 전체 평가 시간 (평가기는 8문항씩 동시 실행). 시간은 평가 단위와 무관하다.

| 방식 | page 평가 k=5 / 10 / 20 (최초 실행) | document 평가 k=5 / 10 / 20 |
|---|---|---|
| Naive | 1.6 / 0.9 / 1.0초 | 0.9 / 0.7 / 0.7초 |
| Hybrid | 10.4 / 4.6 / 5.4초 | 4.3 / 4.2 / 4.1초 |
| Hybrid + Rerank | 118.6 / 109.8 / 109.4초 | 78.8 / 77.8 / 78.0초 |

- 같은 환경에서 page 평가를 다시 돌린 대조군(Hybrid + Rerank)도 77.5~77.9초였다. 최초 page 실행의 109~119초가 더 길었던 이유는 확인하지 않았다(k=5는 CPU 평가를 동시에 돌리고 있었다). 대표값으로 **약 78초(질문당 약 1.3초)**를 쓴다.
- 리랭커가 검색 시간의 대부분을 차지한다. 후보 수가 50개로 고정이라 **k를 바꿔도 리랭킹 시간은 거의 같다.**

리랭커 단독 측정 (GPU, 질문 20개를 하나씩, 모델 로딩 제외)

| 단위 | 평균 | 범위 |
|---|---|---|
| 배치 1개 (32쌍) | 0.89초 | 0.50 ~ 1.34초 |
| 질문 1개 (50쌍 = 32 + 18) | 1.28초 | 0.83 ~ 1.79초 |
| 모델 로딩 + 첫 호출 | 4.63초 | 처음 한 번 |

- 평가기는 8문항을 동시에 보내지만 리랭커가 잠금 때문에 하나씩 처리하므로, 전체 시간은 순서대로 돌린 것(1.28초 × 60 ≈ 77초)과 비슷하다.
- CPU 환경(api 기본 실행 기준)에서는 리랭킹에 질문당 8~17초가 걸렸다. 동시 요청이 몰리면 잠금 대기로 더 길어진다.

## 7. 한계와 해석 시 주의

- **문항 수가 적다.** 채점 문항은 56개다. 평균 0.02 안팎의 차이는 우연과 구별하기 어렵다.
- **Recall 상한.** 근거 그룹이 6개 이상인 문항이 6개라 k=5에서는 Recall 만점이 어렵다. Recall은 k와 함께 읽는다.
- **document Hit의 변별력.** document 단위 Hit는 거의 모든 곳에서 1.000이라 방식을 구분하지 못한다. 문서 단위에서는 Recall을 본다.
- **방식 간 점수 비교.** Hit·Recall은 같은 인덱스·같은 골든 데이터셋에서 방식끼리 비교한다. 리랭커 점수와 RRF 점수처럼 방식 내부의 검색 점수는 척도가 달라 비교하지 않는다.
- **단위 간 점수 비교.** page와 document 점수는 채점 기준이 달라 서로 같은 척도가 아니다. 단위 간 차이는 3.6절처럼 "얼마나 느슨한 기준인가"로 읽는다.
- **다른 인덱스와 비교 금지.** `index_fingerprint`나 `golden_fingerprint`가 다른 결과와는 비교하지 않는다.
- **정답 근거가 하나뿐인 문항.** 같은 뜻의 다른 페이지를 찾아도 page 기준으로는 0점 처리된다(`IS-ADD-10`). 검색 평가가 답변 품질을 그대로 대변하지는 않는다.
- **추가 실험은 page 기준이다.** 5.1(CPU·GPU 비교)과 5.3(BM25 토큰화)의 document 기준 결과는 확인하지 않았다. 5.2는 상위 5개 목록이 같아서 단위와 무관하다.
- **실행 환경.** 평가는 GPU용 torch 2.14.1을 따로 설치한 환경에서 돌렸다. 현재 저장소 환경(torch 2.11.0+cu128)과는 소수점 단위로 다를 수 있다. CPU·GPU 비교(5.1)에서 문항별 결과가 같았으므로 영향은 작을 것으로 본다.
- **평가 문항에 맞춘 조정 주의.** 5.3의 토큰화 규칙은 평가 질문을 보지 않고 일반적인 한국어 조사로 정했다.

## 8. 결론과 다음 단계

**결론**

두 단위의 Hit·Recall을 한눈에 보면 다음과 같다.

| k | 방식 | page Hit | page Recall | document Hit | document Recall |
|---|---|---|---|---|---|
| 5 | Naive | 0.911 | 0.619 | 1.000 | 0.726 |
| 5 | Hybrid | 0.875 | 0.596 | 0.982 | 0.736 |
| 5 | **Hybrid + Rerank** | **0.964** | **0.676** | 1.000 | **0.785** |
| 10 | Naive | 0.982 | 0.689 | 1.000 | 0.789 |
| 10 | Hybrid | 0.946 | 0.700 | 1.000 | 0.823 |
| 10 | **Hybrid + Rerank** | **0.982** | **0.765** | 1.000 | **0.863** |

1. 기본 검색 방식은 **Hybrid + Rerank**가 적합하다. 서비스에 가까운 k=5에서 page Hit는 Naive보다 +0.054, Hybrid보다 +0.089 높고, page Recall은 +0.057 / +0.080 높다. **document Hit는 Naive와 같고(1.000) Hybrid보다 0.018 높을 뿐이라 차이가 거의 없으며**, document Recall은 +0.059 / +0.049 높다.
2. k는 **5~10**이 적당하다. page Hit는 k=10에서 거의 포화하고(0.982), **document Hit는 k=5에서 이미 1.000이다**(Hybrid만 k=10부터). Recall은 k=20까지 오르지만 그만큼 답변 프롬프트의 토큰·비용이 늘어난다.
3. BM25 토큰화(regex)와 리랭커 입력 한도(512)는 **현재 설정을 유지**한다.
4. 답변에 페이지 출처를 붙이므로 **page 기준을 주 지표**로 본다. document 기준은 놓친 이유가 문서 선정인지 페이지 선정인지를 구분하는 데 쓴다. document Hit는 거의 모든 곳에서 1.000이라 방식을 고르는 근거로는 쓰지 않고, 방식 간 차이는 document Recall로 본다. page 기준으로 충족하지 못한 근거 그룹 중 16~21개(방식·k에 따라 다름)는 문서는 맞고 페이지가 틀린 경우다.

**다음 단계 (제안)**
- **RRF 결합 조정**: BM25 순위가 좋아져도 최종 결과에 반영되지 않는 이유가 결합 단계(같은 가중치, `RRF_CONSTANT=60`)에 있는지 확인한다.
- **페이지 선정 개선**: 맞는 문서를 가져오고도 정확한 페이지를 놓치는 구간(178개 그룹 중 9~12%)을 줄이는 방법을 찾는다.
- **답변 평가와 함께 보기**: `IS-ADD-10`처럼 page 기준으로는 0점이지만 답변은 맞을 수 있는 문항을 답변 평가로 확인한다.
- **리랭킹 지연 줄이기**: 시작 시 모델 미리 불러오기, 후보 수 조정(정확도 영향 평가 필요), GPU 실행, 잠금 대기를 latency에서 분리해 측정하기.
- **추가 실험의 document 기준 확인**: 5.1·5.3을 document 기준으로도 확인한다.
