# 리랭커 입력 한도 512 / 1024 / 2048 비교

- 작성일: 2026-11-10
- 대상: `src/retrieval/reranker.py`의 `DEFAULT_MAX_TOKENS` (환경변수 `RERANKER_MAX_TOKENS`)
- 코드: `06f7021` (PR #19 브랜치 `feat/retrieval-evaluator`). 이 실험을 위해 코드를 고치지 않았다.

## 결론

**512를 유지한다.** 세 값에서 Hit@5, Recall@5, 문항별 점수, 상위 5개 순위, 평가 시간이 모두 같았다. 실제로 리랭커에 들어간 질문+청크 쌍 2,800개 중 가장 긴 것이 504토큰이라 512에서도 잘린 쌍이 없었다.

## 왜 실험했나

리랭커(cross-encoder)는 질문과 청크를 붙여 한 입력으로 읽는다.

```
[CLS] 질문 [SEP] 청크 [SEP]   ← 이 전체가 max_tokens 이하여야 한다
```

청크 한도(`max_chunk_tokens`)가 512이고 리랭커 한도도 512이면, 설계상 질문이 들어갈 자리가 없다. 넘치는 쌍은 오류 없이 청크 뒤쪽이 잘린다. 그래서 한도를 1024나 2048로 올려야 하는지 확인했다.

## 실험 조건

| 항목 | 값 |
|---|---|
| 검색 방식 | `hybrid_rerank` (RRF 상위 50개를 리랭킹) |
| k / 단위 | 5 / page |
| 질문 | 골든 60개 (채점 56, 근거 없음 4, 실패 0) |
| 인덱스 | `rag-dev-chanyeongg3`, 청크 15,053개, `intfloat/multilingual-e5-base`, `max_chunk_tokens`=512 |
| 리랭커 | `BAAI/bge-reranker-v2-m3` (모델 자체 한도 8,192토큰) |
| 장치 | RTX 5060 Laptop GPU, torch 2.14.1+cu130 |
| index_fingerprint | `0acd52b3e8804b0d6e07c54dfa396f2d8b01a05402f912b1ceeeca481edbe2f4` |
| golden_fingerprint | `6fb91800a14772fdf63c158d760323b6864d8979f8f9ec1f7fbf3210cb7b1bef` |

- 청크 로딩과 BM25는 한 번만 만들고 리랭커만 바꿔 끼웠다. 리랭커에 들어가는 후보 50개는 세 설정에서 같다.
- 상수를 고치는 대신 `CrossEncoderReranker(max_tokens=n)`으로 값을 넘겼다. 결과는 상수를 바꾼 것과 같다.
- 시간을 재려고 질문을 하나씩 순서대로 처리했고, 모델 로딩 시간은 뺐다.

## 결과

| max_tokens | Hit@5 | Recall@5 | 점수가 바뀐 문항 | 상위 5개가 바뀐 질문 | 평가 시간 |
|---|---|---|---|---|---|
| **512** | 0.964 | 0.676 | 기준 | 기준 | 75.8초 |
| 1024 | 0.964 | 0.676 | 0 / 56 | 0 / 56 | 75.7초 |
| 2048 | 0.964 | 0.676 | 0 / 56 | 0 / 56 | 75.9초 |

평가 시간은 질문당 약 1.35초다. 세 값의 차이(0.2초 이내)는 측정 오차 범위다.

## 왜 같게 나왔나: 실제 쌍 길이

리랭커는 청크 15,053개를 모두 보지 않는다. Dense 검색과 BM25가 먼저 후보를 고르고, RRF로 합친 **상위 50개만** 리랭커에 들어간다(`CANDIDATE_POOL = 50`). 그래서 이번 평가에서 리랭커가 실제로 읽은 쌍은 **채점 질문 56개 × 후보 50개 = 2,800쌍**이 전부다. 근거 없는 4문항은 검색하지 않는다.

이 2,800쌍을 리랭커 토크나이저로 잘라내지 않고 다시 셌다(특수 토큰 포함).

| 항목 | 값 |
|---|---|
| 측정한 쌍 | 2,800 |
| 중앙값 | 190 |
| 상위 1% | 459 |
| 최대 | **504** |
| 512를 넘은 쌍 | 0 |
| 1024를 넘은 쌍 | 0 |
| 2048을 넘은 쌍 | 0 |

- 청킹이 청크를 700자 이하로 자르기 때문에 쌍이 짧다. 넘는 쌍이 없으니 512에서 잘린 입력이 없었고, 한도를 올려도 모델이 읽는 내용은 같다.
- 시간이 같은 이유: 한 묶음의 입력은 설정한 한도가 아니라 그 묶음에서 가장 긴 쌍에 맞춰 길이를 맞춘다. 실제 쌍이 모두 504 이하라 세 설정의 계산량이 같다.

## 판단

- **512 유지.** 이 데이터에서는 손해가 없고, 청킹(`max_chunk_tokens`=512)과 임베더(512) 한도와도 숫자가 맞는다.
- **여유가 8토큰뿐이다.** 가장 긴 쌍이 504라서, 다음 경우에는 다시 잰다.
  - 청크 길이(700자)를 늘릴 때
  - 질문이 지금보다 길어질 때
  - 평가 문항이 바뀔 때
- **1024로 바꾸는 비용은 작다.** 속도 차이가 없었으므로 위 상황이 생기면 `RERANKER_MAX_TOKENS=1024`로 환경변수만 바꾸면 된다.
- **2048은 이점이 없다.** 1024를 넘는 쌍이 하나도 없다.

## 남은 한계

- `check_chunk_limit`은 청크 한도만 비교하고 질문 길이는 세지 않는다. "잘리지 않는다"는 이번 평가 질문에서 잰 결과이고, 코드가 보장하는 성질은 아니다. 다른 질문에서 긴 청크가 후보 50개에 들어오면 넘칠 수 있다.
- 저장소의 torch는 `2.15.0+cpu`다. 이 실험은 GPU용 torch 2.14.1을 따로 설치한 환경에서 돌렸다. 세 설정은 같은 환경이라 서로 비교할 수 있지만, 다른 환경의 수치와는 소수점 단위로 다를 수 있다.
- 평가 시간은 GPU 기준이다. CPU에서는 질문당 약 18초가 걸렸다(이전 측정).

## 재현

환경변수만으로 같은 비교를 할 수 있다. 실제 색인과 Qdrant가 필요하다.

```bash
RETRIEVAL_IMPL=real CHUNKING_IMPL=real INDEX_NAME=rag-dev-chanyeongg3 \
RERANKER_MAX_TOKENS=1024 uv run python -m app.cli eval --k 5 --unit page
```

이 보고서의 수치는 리랭커만 바꿔 끼우고 쌍 길이를 함께 기록하는 별도 스크립트로 냈다. 스크립트는 저장소에 넣지 않았다.
